# n8n 주간 운영 리포트 스킬

n8n-mcp로 한 주의 운영 현황을 모아 리포트 메시지를 만들고, 사용자 확인을 받은 뒤 Slack으로 보내는 스킬.

## 원칙

- **포맷은 [docs/n8n-ops-report-format.md](../../../docs/n8n-ops-report-format.md)만 따른다.** 구성, 구역별 규칙, 템플릿, 전송 채널이 모두 그 문서에 있다. 사용자가 편집하는 문서이므로 매번 새로 읽고, 이 스킬에 포맷을 복사해 두지 않는다.
- **읽기 전용이다.** 워크플로우와 실행 기록을 고치거나 지우지 않는다. 필요한 조치는 리포트의 "해결책"과 "확인 필요"에 제안으로만 적는다.
- **증거로 판단한다.** 실행 기록과 워크플로우 설정에서 확인한 것만 적고, 확인하지 못한 것은 "확인하지 못했다"고 적는다.
- `.claude/rules/n8n/common.md`의 공통 규칙을 따른다.

## 대상 기간

- 기본: 그 주 월요일 00:00 KST부터 작성 시점까지
- 스킬 인자로 기간을 받으면 그 기간을 쓴다 (예: `/n8n-ops-report 지난주`, `/n8n-ops-report 11-09~11-15`)
- n8n-mcp 응답의 시각은 UTC다. KST(+9시간)로 바꿔 기간을 판정하고 표기한다

## 절차

### 1. 준비

1. `n8n_health_check`로 인스턴스 상태를 확인한다
2. 포맷 문서를 읽는다

### 2. 수집

| 순서 | 호출 | 얻는 것 |
|------|------|---------|
| 1 | `n8n_list_workflows` | 전체 목록, 활성 여부, 생성 시각, 노드 수 |
| 2 | `n8n_executions` list, `status: "error"` | 기간 안의 실패 실행 |
| 3 | `n8n_executions` list (필터 없음) | 성공·대기 실행, 워크플로우별 마지막 실행 |
| 4 | `n8n_executions` list, `workflowId`, `limit: 1` | 3번에 나오지 않은 활성 워크플로우의 마지막 실행 |

- 3번은 기간 시작 전 기록이 나올 때까지만 `cursor`로 다음 쪽을 받는다
- 1~3번은 서로 의존하지 않으므로 한 번에 호출한다

### 3. 신규 워크플로우

`createdAt`이 대상 기간 안인 워크플로우를 생성 순으로 고른다.

### 4. 에러 분석

1. 기간 안의 실패 실행마다 `n8n_executions` get, `mode: "error"`, `errorItemsLimit: 0`으로 조회한다
   - `errorItemsLimit`을 주지 않으면 앞 노드의 샘플 데이터가 통째로 딸려 와 응답이 매우 커진다
2. 원인별로 묶는다
   - 같은 워크플로우, 같은 노드, 같은 에러 메시지는 한 항목
   - 메인 실행의 `error.executionId`가 서브 워크플로우 실행을 가리키면 전파된 것이다. 한 항목으로 묶고 실제 사고 건수를 적는다
3. 항목마다 상태를 정한다

   | 상태 | 조건 |
   |------|------|
   | `해결됨` | 같은 워크플로우의 이후 실행이 성공했고, 고친 내용을 `n8n_get_workflow` `mode: "filtered"`로 확인함 |
   | `조치 불필요` | 스택에 `partial-execution-utils/find-start-nodes`가 있고 실행된 노드가 0개 (에디터 부분 실행 오류) |
   | `미해결` | 그 밖의 경우 |

4. 미해결 항목에는 실패한 노드와 에러 응답을 근거로 해결책을 적는다

### 5. 휴면 워크플로우

- 활성 워크플로우 중 마지막 실행이 30일 이상 지난 것을 고른다
- 실행 기록만으로 단정하지 않는다
  - 실행 기록은 14일만 보관된다
  - 성공 실행을 저장하지 않는 워크플로우는 기록이 실제보다 오래돼 보인다
  - 기록이 없으면 휴면으로 적지 않고 "실행 기록 없음"으로 적는다

### 6. 확인 필요 항목

수집한 데이터에서 다음을 찾는다.

- `waiting` 상태로 남아 있는 실행
- 게시된 워크플로우가 실패했는데 에러 워크플로우의 실행 기록이 없는 경우
- 스케줄 실행이 예정 시각과 다르게 시작됐거나 빠진 경우

### 7. 작성과 전송

1. 포맷 문서의 템플릿과 구역별 규칙대로 메시지를 만든다
2. 완성한 메시지를 대화에 보여주고 전송할지 확인받는다
3. 승인받으면 Slack 커넥터의 `slack_send_message`로 포맷 문서의 "전송 채널"에 보낸다
4. 전송 뒤 메시지 링크를 알려준다

전송할 때 지킬 것:

- 한 메시지는 5,000자 이내다. 넘으면 구역 단위로 나눠 첫 메시지의 스레드 답글로 잇는다
- 사용자가 고쳐 달라고 하면 고친 메시지를 다시 보여주고 확인받는다
- Slack 커넥터가 연결돼 있지 않으면 보내지 않고 메시지 원문을 넘긴다
