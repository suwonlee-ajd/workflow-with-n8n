# 운영 관리자

n8n 워크플로우의 모니터링, 디버깅, 실행 관리를 담당하는 모듈.

## 모니터링

### 전체 현황 파악
1. `n8n_list_workflows`로 전체 워크플로우 목록 조회
2. 각 워크플로우의 활성/비활성 상태 확인
3. 워크플로우 수, 활성 비율 요약

### 실행 이력 분석
1. `n8n_executions`로 최근 실행 이력 조회
2. 성공/실패/대기 상태별 분류
3. 자주 실패하는 워크플로우 식별
4. 실행 시간 패턴 분석 (느린 워크플로우 감지)

### 상태 보고 형식
```
## n8n 워크플로우 현황

### 전체 요약
- 전체 워크플로우: N개 (활성: X개, 비활성: Y개)
- 최근 24시간 실행: N회 (성공: X회, 실패: Y회)

### 주의 필요 워크플로우
| 워크플로우 | 상태 | 최근 실패 | 실패율 |
|---|---|---|---|
| ... | ... | ... | ... |
```

## 디버깅

### 실패 원인 분석 프로세스
1. `n8n_executions`로 실패한 실행 조회
2. 에러 메시지와 실패한 노드 식별
3. `n8n_get_workflow`로 해당 워크플로우 구조 확인
4. 원인 분류:
   - **연결 에러**: 외부 서비스 접근 불가 (API 키 만료, URL 변경 등)
   - **데이터 에러**: 예상과 다른 입력 데이터 형식
   - **로직 에러**: 조건 분기 오류, 누락된 필드 처리
   - **리소스 에러**: 타임아웃, 메모리 초과

### 자동 수정 시도
autofix는 구조·검증 오류 수정 도구 (실행 중 오류의 원인은 수정 대상 아님)
1. `n8n_validate_workflow`로 구조·검증 오류가 있을 때만 사용
2. `n8n_autofix_workflow`를 `applyFixes: false`로 실행해 수정안 미리보기
3. 수정안(특히 typeVersion 업그레이드)을 사용자에게 보여주고 승인 후 `applyFixes: true`로 적용
4. 적용 후 `n8n_validate_workflow`로 재검증, 해당 없거나 실패 시 수동 수정안 제시

### 수동 수정 적용
1. 수정안을 사용자에게 구체적으로 설명
2. 사용자 승인 후 `n8n_update_partial_workflow`로 패치
3. 수정 후 `n8n_validate_workflow`로 검증
4. 가능한 경우 `n8n_test_workflow`로 테스트

### 롤백
- 수정이 실패하거나 상황이 악화되면 `n8n_workflow_versions`의 rollback 모드 사용 (SKILL.md '안전 원칙'의 롤백 제약 준수)
- 롤백 전 사용자에게 "이전 버전으로 되돌리겠습니다. 마지막 스냅샷 이후 n8n UI에서 고친 내용은 덮어써집니다" 확인

## 실행 관리

### 수동 테스트
- `n8n_test_workflow`로 즉시 실행 (webhook/form/chat 트리거 + 활성 상태만, SKILL.md '테스트 제약사항' 참고)
- 테스트 데이터가 필요한 경우 사용자에게 요청하거나 샘플 데이터 제안
- 스케줄 트리거 워크플로우는 "n8n UI에서 'Execute workflow' 버튼을 눌러주세요" 안내

### 워크플로우 삭제
- `.claude/rules/n8n/common.md` HARD RULE을 충족할 때만 진행 (대상을 이름·ID로 명시한 삭제 요청)
- 실행 직전 확인 문구: "워크플로우 '[이름]' (ID: [ID])을 삭제하시겠습니까? 이 작업은 되돌릴 수 없습니다."
- 삭제 전 SKILL.md '안전 원칙'의 단일 워크플로우 백업 실행 (스냅샷 롤백은 기존 워크플로우를 덮어쓰는 방식이라 삭제 복구용 아님)

### 버전 관리
- `n8n_workflow_versions`로 변경 이력 조회 (n8n-mcp로 수정한 이력만. 워크플로우당 최근 10개까지 보관하며, 일정 기간이 지난 스냅샷도 자동 삭제)
- `diff` 모드로 두 스냅샷을 비교하고, 특정 버전으로 rollback 가능
- 스냅샷은 n8n-mcp가 수정 직전 자동 저장 (수동 저장 기능 없음)

## 핵심 원칙

1. **안전 우선**: 파괴적 작업은 항상 사용자 확인 후 실행
2. **증거 기반**: 실행 로그와 에러 메시지를 기반으로 판단, 추측 최소화
3. **자동 → 수동 에스컬레이션**: 검증 오류는 autofix 미리보기 → 승인 → 적용, 실행 오류는 원인 분석 후 수동 수정
4. **롤백 대비**: 스냅샷이 없는 워크플로우(UI에서 만들거나 고친 것)는 수정 전 SKILL.md '안전 원칙'의 단일 워크플로우 백업 실행
5. **이름 규칙**: 워크플로우를 만들거나 이름을 바꿀 때는 workflow-builder.md '네이밍 컨벤션'을 따른다 (일괄 정리 절차도 같은 파일의 '이름 일괄 정리')

## 에러 트리거 관리

Error Trigger는 별도 에러 워크플로우에 두고, 감시할 워크플로우의 설정 `errorWorkflow`에 그 ID를 지정해야 동작 (각 워크플로우에 노드만 추가하면 동작하지 않음)

### 현황 조회
"에러 트리거 현황 보여줘" 요청 시:
1. `n8n_list_workflows`로 워크플로우 ID 목록 조회 (목록에는 nodes·settings 없음)
2. 워크플로우별 `n8n_get_workflow`로 `settings.errorWorkflow` 지정 여부 확인
3. 결과를 표로 출력:

| # | 워크플로우 | 상태 | 에러 워크플로우 |
|---|----------|------|-----------|
| 1 | [메인] 브리핑: AI 아침 요약 | 활성 | [에러] 공통: 실패 알림 |
| 2 | [메인] CS: 고객 문의 분류 | 활성 | **미지정** |

### 일괄 등록
"전체 워크플로우에 에러 트리거 등록해줘" 요청 시:
1. Error Trigger 노드가 있는 에러 워크플로우 확인, 없으면 생성 제안 (Error Trigger → 알림 노드, 알림 대상은 사용자에게 확인. 이름은 `[에러] 공통: 실패 알림`처럼 workflow-builder.md '네이밍 컨벤션' 형식)
2. `errorWorkflow` 미지정 활성 워크플로우 목록과 지정할 에러 워크플로우를 보여주고 확인을 구한다
3. 확인 후 각 워크플로우에 `n8n_update_partial_workflow`의 `updateSettings`로 `errorWorkflow` 지정 (노드 추가·전체 덮어쓰기 없음)
4. 결과 리포트 출력

## 휴면 유저 위험 감지

> 학습용 셀프호스팅(계정이 몇 개뿐인) 환경이라 현재는 참고용. n8n-mcp에 유저 조회 도구가 없으므로
> 요청 시 "현재 MCP로 지원하지 않음" 안내. `.env`의 API 키를 읽어 n8n API를 직접 호출하지 않음.

"휴면 유저 중 워크플로우 가진 사람 보여줘" 요청 시:
1. 유저 목록에서 90일+ 미접속 유저 필터링
2. 각 휴면 유저의 소유 워크플로우 개수 조회
3. 워크플로우를 보유한 휴면 유저만 표로 출력

## 결과 출력 포맷

모니터링/분석 결과는 항상 표 형식으로 정리하여 보여준다.

**워크플로우 현황 예시:**

| # | 이름 | 상태 | 최근 실행 | 결과 |
|---|------|------|----------|------|
| 1 | [메인] 브리핑: AI 아침 요약 | 활성 | 2026-03-26 09:00 | 성공 |
| 2 | [메인] CS: 고객 문의 분류 | 활성 | 2026-03-26 14:32 | 실패 |

**에러 리포트 예시:**

| # | 워크플로우 | 에러 타입 | 발생 시각 | 원인 요약 |
|---|----------|----------|----------|----------|
| 1 | [메인] CS: 고객 문의 분류 | NodeOperationError | 03-26 14:32 | API 키 만료 |

**유저 현황 예시:**

| # | 이메일 | 역할 | 최근 접속 | 미접속 일수 | 상태 |
|---|--------|------|----------|-----------|------|
| 1 | admin@co.kr | Owner | 오늘 | 0 | 정상 |
| 2 | dormant@co.kr | Member | 2025-10-01 | 176 | 휴면 |
