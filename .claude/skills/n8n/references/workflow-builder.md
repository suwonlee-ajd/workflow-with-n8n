# 워크플로우 빌더

자연어 요청을 n8n 워크플로우로 변환하고, 기존 워크플로우를 분석/개선하는 모듈.

## 네이밍 컨벤션

워크플로우를 만들거나 고칠 때, 기존 워크플로우를 점검할 때 이 규칙을 따른다.

### 워크플로우 이름

형식: `[유형] 도메인: 기능`

| 부분 | 규칙 | 예시 |
|------|------|------|
| `[유형]` | 워크플로우의 실행 역할. 아래 세 가지 중 하나 | `[메인]`, `[서브]`, `[에러]` |
| 도메인 | 팀명 또는 업무 영역. 여러 곳에서 쓰는 것은 `공통`. 새 도메인을 만들기 전에 `n8n_list_workflows`로 기존 도메인을 확인 | `주식`, `브리핑`, `공통` |
| 기능 | 무엇을 하는지 한국어로 간결하게. 도메인에 쓴 단어를 다시 쓰지 않는다 | 일별 시세 가져오기, 전국 아침 뉴스 |

유형:

| 유형 | 기준 |
|------|------|
| `메인` | 스케줄·웹훅·폼·채팅·수동 트리거로 직접 시작한다 |
| `서브` | Execute Workflow Trigger가 있어 다른 워크플로우나 AI Agent가 호출한다. 직접 실행용 수동 트리거가 함께 있어도 서브 |
| `에러` | Error Trigger로 시작한다. 다른 워크플로우의 `settings.errorWorkflow`에 지정되어 그 워크플로우가 실패하면 실행된다 |

도메인 단어를 기능에 반복하지 않는다:
- `[메인] 브리핑: 전국 아침 브리핑`이 아니라 `[메인] 브리핑: 전국 아침 뉴스`

이름에 넣지 않는 것:
- 트리거 종류(Schedule, Webhook 등)와 실행 시각(예: 매일 09:00): 워크플로우 description이나 스티키 노트에 쓴다. 트리거는 `n8n_get_workflow`(structure)로 확인한다
- 운영 상태(테스트, 폐기예정 등): 태그로 관리한다
- 도메인을 폴더로 대신하지 않는다. MCP로 워크플로우의 폴더 위치를 읽을 수 없다

예시:
- `[메인] 주식: 국내 종목 선별`
- `[서브] 주식: 일별 시세 가져오기`
- `[메인] 브리핑: 전국 아침 뉴스`
- `[에러] 공통: 실패 알림`

### 노드 이름

- 하는 일을 한국어로 쓴다 (예: `전국 날씨 조회`, `뉴스 목록 합치기`, `Slack 브리핑 전송`). 서비스명 같은 기술 용어는 원어 그대로
- `HTTP Request`, `Edit Fields1` 같은 기본 이름을 그대로 두지 않는다
- 서브 워크플로우의 마지막 Set 노드는 `결과 반환`

### 표준 그룹 구성

노드를 단계별 캔버스 그룹(n8n 2.28+)으로 묶는다. ETL이 아닌 워크플로우도 같은 틀을 쓴다. 그룹은 보기용이라 실행에는 영향이 없다.

| 그룹 이름 | 들어가는 노드 |
|----------|--------------|
| `1. 시작` | 트리거 바로 다음 노드: 입력 정리, 설정값, 시작 알림 |
| `2. 수집 (Extract)` | 원천 조회(DB·API·RSS·파일)와 응답 정리(펼치기·필드 꺼내기·합치기) |
| `3. 가공 (Transform)` | 여러 소스 결합, 계산·판단·필터, AI 요약 |
| `4. 적재·전달 (Load)` | DB·시트 저장, 메시지 발송, 웹훅 응답 |
| `5. 종료` | 종료 알림, 실행 기록, 서브 워크플로우 결과 반환 |

- 해당 단계의 노드가 없으면 그 그룹은 만들지 않는다. 번호는 표준 번호를 그대로 쓴다 (빠진 번호가 있어도 된다)
- 시작·종료 알림은 메신저나 솔루션 연동이 있을 때만 둔다
- 수집 사이에 낀 응답 정리 노드는 수집 그룹에 넣는다. 그룹은 연달아 이어진 노드만 묶을 수 있어서 정리 노드만 떼어 가공으로 보낼 수 없다
- 실패 알림은 그룹에 넣지 않는다. 에러 워크플로우(Error Trigger)를 만들어 `settings.errorWorkflow`에 지정한다 ('복잡한 패턴 > 에러 핸들링' 참고)

n8n이 저장할 때 거부하는 그룹:
- 트리거 노드가 들어간 그룹. 트리거는 그룹 왼쪽에 따로 둔다
- 입구나 출구가 둘 이상인 그룹. 그룹 안에서 갈라졌다 합쳐지는 것은 괜찮지만, 에러 출력처럼 그룹 밖으로 나가는 갈래가 하나 더 있으면 안 된다
- 서로 이어지지 않은 노드를 묶은 그룹

작성 방법:
- 새로 만들 때: `n8n_create_workflow`의 `nodeGroups`에 `{name, nodeIds, description}`을 넣는다 (멤버는 노드 ID)
- 기존 워크플로우: `n8n_update_partial_workflow`의 `setNodeGroups` 연산. 목록 전체를 교체하므로 유지할 그룹도 모두 넣는다
- `description`은 155자까지 (n8n 2.32+)
- 저장 후 `n8n_get_workflow`(structure)로 `nodeGroups`를 확인하고, 수정 응답의 `details.warnings`에 그룹 해제 경고가 없는지 본다

### 설명 스티키 노트

`example-1~3`(n8n 기본 예제)을 뺀 모든 워크플로우에 설명 스티키 노트(Sticky Note)를 하나 둔다. 노드 이름은 `설명`이고, 맨 위 세 줄은 아래 형식으로 고정한다.

```markdown
![아정당](/static/ajd-logo.png)
## 주식: 국내 종목 선별
평일 08:10(또는 폼 제출)에 거래대금 상위 150종목에서 상승·하락 추세 종목을 골라 Slack으로 전송
```

| 줄 | 규칙 |
|----|------|
| 로고 | `![아정당](/static/ajd-logo.png)` 그대로. 50x50 px 로 보임 |
| 제목 | `## ` 뒤에 워크플로우 이름에서 `[유형]`을 뺀 `도메인: 기능` |
| 요약 | 1~2줄, 명사형 종결. 언제(트리거·실행 시각) 무엇을 해서 결과를 어디로 보내는지. 서브는 누가 부르는지 |

- 그 아래에는 필요한 것만 쓴다: 흐름, 입력·출력(서브), 준비 사항(크리덴셜·채널 선택), 주의 사항. 소제목은 `**굵게**`
- 문체: 요약과 본문 모두 [docs/code-style.md](../../../../docs/code-style.md) 1장 '주석'처럼 두괄식·명사형 종결. 기존 스티키 본문에 남은 `~합니다`·`~한다` 는 그 워크플로우를 고칠 때 맞춘다
- 기존 워크플로우를 고칠 때 설명 스티키가 없거나 규칙과 다르면, 보완안을 요청받은 수정과 함께 보여 주고 승인받아 같이 고친다

위치와 크기:

| 항목 | 규칙 |
|------|------|
| 왼쪽 | 맨 왼쪽 노드의 x 와 같게 |
| 위쪽 | 가장 위 노드보다 위. 스티키 아래쪽(`y + height`)과 가장 위 노드 사이 60px 이상 |
| 크기 | 로고·제목·요약만 있으면 `width` 480, `height` 200. 내용이 늘면 `height` 를 늘리고 그만큼 `y` 를 줄여 위쪽으로 키운다 (노드와 겹치지 않도록) |

- 지정 방법: 노드 `position`, `parameters.width`·`height`. 캔버스 그룹과 달리 n8n 이 거부하는 조건은 없다
- 로고 이미지
  - 파일: 저장소의 `assets/ajd-logo.png` (50x50 px). compose 가 n8n 편집기의 static 폴더에 연결해 `/static/ajd-logo.png` 로 보인다
  - 크기는 파일 크기로만 정해진다. n8n 2.44.7 스티키는 HTML(`<img width>`)을 막아 이미지를 원본 크기로 보여 준다. 크기를 바꾸려면 파일을 바꾼다
  - 주소는 `https://…` 나 `/static/<파일>.png`(jpg·jpeg·gif·webp)만 표시된다. `data:` 주소나 다른 경로는 지워진다

## 워크플로우 생성 프로세스

### 1단계: 요청 분석
- 사용자 요청에서 트리거 유형, 처리 로직, 출력 대상을 식별
- 필요한 노드 목록을 추출
- 워크플로우 이름을 '네이밍 컨벤션' 형식으로 정한다. 먼저 `n8n_list_workflows`로 같은 도메인의 기존 워크플로우를 확인해 중복을 피한다

### 2단계: 노드 검색 및 확인
- `search_nodes`로 필요한 노드 검색
- `get_node`로 각 노드의 파라미터, 입출력 스펙 확인
- `validate_node`로 노드 설정이 유효한지 검증

### 3단계: 워크플로우 JSON 구성
- 노드 배열, 연결(connections), 설정(settings) 구성
- 노드 포지션 배치: 좌→우로 300px 간격, 분기 시 상하로 200px 간격
- 트리거 노드는 항상 가장 왼쪽 (position: [250, 300])
- 노드 이름은 '네이밍 컨벤션 > 노드 이름'을 따르고, '표준 그룹 구성'대로 `nodeGroups`를 만든다
- '설명 스티키 노트'를 캔버스 왼쪽 위에 넣는다

### 4단계: 사전 검증
- `validate_workflow`로 JSON 구조 검증
- 에러 발생 시 수정 후 재검증
- `n8n_autofix_workflow` 활용 가능

### 사용자 미리보기 (생성 전 확인)

생성 실행 전에 사용자에게 다음 정보를 표로 보여주고 확인을 받는다:

| 항목 | 내용 |
|------|------|
| 워크플로우 이름 | 제안된 이름 (네이밍 컨벤션 형식) |
| 트리거 | 트리거 노드 타입 + 설정 요약 |
| 노드 구성 | 전체 노드 목록 (순서대로) |
| 연결 | 노드 간 연결 흐름 (A → B → C) |
| 그룹 | 그룹별 노드 (표준 그룹 구성) |
| 초기 상태 | 비활성 (테스트 시 1회성/계속 사용 여부 확인) |

"위 구성으로 워크플로우를 생성합니다. 진행할까요?"

### 5단계: 생성 및 테스트
- `n8n_create_workflow`로 워크플로우 생성
- webhook/form/chat 트리거인 경우 `n8n_test_workflow`로 테스트
- 스케줄 트리거인 경우 "n8n UI에서 수동 실행으로 테스트해주세요" 안내

### 6단계: 결과 보고
- 생성된 워크플로우 ID, 이름, 노드 구성 요약
- 테스트 결과 (성공/실패 및 출력 데이터)
- n8n UI에서 확인할 수 있는 안내

## 복잡한 패턴

### 에러 핸들링
- Error Trigger 노드로 별도 에러 워크플로우를 만들고, 워크플로우 설정 `errorWorkflow`에 지정해 실패 시 알림
- 개별 노드에 onError 설정: `stopWorkflow`(기본, 중단) / `continueRegularOutput`(오류를 일반 출력으로 계속) / `continueErrorOutput`(오류 전용 출력으로 분기)
- 에러 알림 대상: 이메일, 슬랙, 텔레그램 등 사용자 선호에 따라 설정

### 조건 분기
- IF 노드: 단순 조건 (true/false 분기)
- Switch 노드: 다중 조건 분기 (3개 이상 경로)
- 분기 후 각 경로의 노드를 상하로 배치하여 시각적 구분

### 반복 루프
- Loop Over Items(SplitInBatches) 노드: 대량 데이터를 배치 단위로 처리
- 배치 크기 기본값은 1, API 제한이 허용하는 만큼 키워서 사용
- 루프 완료 후 Merge 노드로 결과 취합

### 서브 워크플로우
- Execute Workflow 노드로 다른 워크플로우 호출
- 공통 로직을 서브 워크플로우로 분리하여 재사용
- 파라미터 전달: JSON 데이터로 입력값 전달

## 기존 워크플로우 분석/개선

### 분석 프로세스
1. `n8n_get_workflow`로 워크플로우 구조 조회
2. 다음 항목 점검:
   - 에러 핸들링 누락 여부
   - 불필요한 중복 노드
   - 비효율적 데이터 처리 (전체 로드 vs 필터링)
   - 하드코딩된 값 (변수로 대체 가능 여부)
   - 워크플로우·노드 이름이 '네이밍 컨벤션'에 맞는지
   - 그룹이 '표준 그룹 구성'을 따르는지
   - '설명 스티키 노트'가 있고 로고·제목·요약 형식, 문체, 위치·크기에 맞는지
3. 개선안을 구체적으로 제시 (어떤 노드를 어떻게 변경할지)

### 개선 적용
- 사용자 승인 후 `n8n_update_partial_workflow`로 부분 수정
- 구조 변경이 큰 경우 `n8n_update_full_workflow` 사용
- 수정 전 스냅샷은 n8n-mcp가 자동 저장 (UI에서 고친 내용은 미포함 → 필요 시 SKILL.md '안전 원칙'의 단일 워크플로우 백업 실행)

### 이름 일괄 정리
"워크플로우 이름을 컨벤션에 맞게 정리해줘" 요청 시:
1. `n8n_list_workflows`로 전체 목록(이름, ID, active 상태) 조회
2. 컨벤션에 맞지 않는 워크플로우만 추리고, 각각 `n8n_get_workflow`(structure)로 트리거 노드를 확인해 유형(메인·서브·에러)을 정하고 새 이름을 제안한다. 이름만으로 기능을 알 수 없으면 노드 구성을 보고 정한다
3. 서브 워크플로우(유형 `서브`) 이름을 바꿀 때는 호출하는 워크플로우의 Execute Workflow 노드가 이름이 아니라 ID로 참조하는지 확인한다
4. 변경표(현재 이름 → 새 이름)를 보여주고 "이대로 변경할까요?" 확인을 받는다
5. 확인 후 `n8n_update_partial_workflow`의 `updateName` 연산으로 이름만 바꾼다 (노드·연결 보존)
6. `n8n_list_workflows`로 새 이름과 active 상태가 그대로인지 확인하고 결과를 보고한다

## 데이터 테이블 연동

- `n8n_manage_datatable`로 테이블 조회/삽입/업데이트
- 활용 예시: 상태 추적, 설정값 저장, 룩업 테이블
- 워크플로우 내에서 데이터 테이블 노드와 연결하여 영구 상태 관리

## 자주 쓰는 노드 조합 가이드

### 웹훅 → 처리 → 응답
- Webhook → Code/Set → Respond to Webhook
- API 엔드포인트 구축에 적합

### 스케줄 → 수집 → 알림
- Schedule Trigger → HTTP Request → IF → Slack/Email
- 주기적 모니터링에 적합

### 트리거 → 분기 → 다중 출력
- Webhook/Schedule → Switch → 각 경로별 처리
- 조건에 따라 다른 서비스로 데이터 전달

### 데이터 동기화
- Schedule Trigger → HTTP Request(소스) → Code(변환) → HTTP Request(대상)
- 서비스 간 데이터 동기화에 적합
