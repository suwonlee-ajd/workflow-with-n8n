# 주간 운영 리포트

n8n-mcp로 한 주의 운영 현황을 모아 리포트 메시지를 만들고, 사용자 확인을 받은 뒤 Slack으로 보내는 모듈.

## 원칙

- **읽기 전용이다.** 워크플로우와 실행 기록을 고치거나 지우지 않는다. 필요한 조치는 리포트의 "해결책"과 "확인 필요"에 제안으로만 적는다.
- **증거로 판단한다.** 실행 기록과 워크플로우 설정에서 확인한 것만 적고, 확인하지 못한 것은 "확인하지 못했다"고 적는다.
- **보내기 전에 확인받는다.** 완성한 메시지를 대화에 먼저 보여주고, 승인받은 뒤 보낸다.

## 기준

- 대상 기간: 그 주 월요일 00:00부터 작성 시점까지 (KST). 요청에 기간이 있으면 그 기간을 쓴다 (예: "지난주 운영 리포트")
- 시각 표기: KST, `MM-DD HH:mm`. n8n-mcp 응답의 시각은 UTC이므로 KST(+9시간)로 바꿔 기간을 판정하고 표기한다
- 전송 채널: `C0BDULL98NL`
- 표 대신 목록을 쓴다 (Slack 메시지에 표를 여러 개 넣기 어렵다)
- 워크플로우 이름은 백틱으로 감싼다

## 절차

### 1. 수집

`n8n_health_check`로 인스턴스 상태를 확인한 뒤 다음을 조회한다.

| 순서 | 호출 | 얻는 것 |
|------|------|---------|
| 1 | `n8n_list_workflows` | 전체 목록, 활성 여부, 생성 시각, 노드 수 |
| 2 | `n8n_executions` list, `status: "error"` | 기간 안의 실패 실행 |
| 3 | `n8n_executions` list (필터 없음) | 성공·대기 실행, 워크플로우별 마지막 실행 |
| 4 | `n8n_executions` list, `workflowId`, `limit: 1` | 3번에 나오지 않은 활성 워크플로우의 마지막 실행 |

- 3번은 기간 시작 전 기록이 나올 때까지만 `cursor`로 다음 쪽을 받는다
- 1~3번은 서로 의존하지 않으므로 한 번에 호출한다

### 2. 신규 워크플로우

`createdAt`이 대상 기간 안인 워크플로우를 생성 순으로 고른다.

### 3. 에러 분석

1. 기간 안의 실패 실행마다 `n8n_executions` get, `mode: "error"`, `errorItemsLimit: 0`으로 조회한다
   - `errorItemsLimit`을 주지 않으면 앞 노드의 샘플 데이터가 통째로 딸려 와 응답이 매우 커진다
2. 원인별로 묶는다
   - 같은 워크플로우, 같은 노드, 같은 에러 메시지는 한 항목
   - 메인 실행의 `error.executionId`가 서브 워크플로우 실행을 가리키면 전파된 것이다. 한 항목으로 묶고 실제 사고 건수를 적는다
3. 항목마다 상태를 정한다

   | 상태 | 조건 |
   |------|------|
   | `해결됨` | 같은 워크플로우의 이후 실행이 성공했고, 고친 내용을 `n8n_get_workflow` `mode: "filtered"`로 확인함 |
   | `조치 불필요` | 스택에 `partial-execution-utils/find-start-nodes`가 있고 실행된 노드가 0개 (에디터 부분 실행 오류) |
   | `미해결` | 그 밖의 경우 |

4. 미해결 항목에는 실패한 노드와 에러 응답을 근거로 해결책을 적는다

원인 분류와 수정 절차는 [ops-manager.md](ops-manager.md)의 '디버깅'을 따른다. 리포트에서는 수정하지 않고 제안만 한다.

### 4. 휴면 워크플로우

- 활성 워크플로우 중 마지막 실행이 30일 이상 지난 것을 고른다
- 실행 기록만으로 단정하지 않는다
  - 실행 기록은 14일만 보관된다
  - 성공 실행을 저장하지 않는 워크플로우는 기록이 실제보다 오래돼 보인다
  - 기록이 없으면 휴면으로 적지 않고 "실행 기록 없음"으로 적는다

### 5. 확인 필요 항목

수집한 데이터에서 다음을 찾는다.

- `waiting` 상태로 남아 있는 실행
- 게시된 워크플로우가 실패했는데 에러 워크플로우의 실행 기록이 없는 경우
- 스케줄 실행이 예정 시각과 다르게 시작됐거나 빠진 경우

### 6. 작성과 전송

1. 아래 '메시지 포맷'대로 메시지를 만든다
2. 완성한 메시지를 대화에 보여주고 전송할지 확인받는다
3. 승인받으면 Slack 커넥터의 `slack_send_message`로 전송 채널에 보낸다
4. 전송 뒤 메시지 링크를 알려준다

전송할 때 지킬 것:

- 한 메시지는 5,000자 이내다. 넘으면 구역 단위로 나눠 첫 메시지의 스레드 답글로 잇는다
- 사용자가 고쳐 달라고 하면 고친 메시지를 다시 보여주고 확인받는다
- Slack 커넥터가 연결돼 있지 않으면 보내지 않고 메시지 원문을 넘긴다

## 메시지 포맷

### 구성

| 순서 | 구역 | 내용 |
|------|------|------|
| 1 | 제목 | 리포트 이름과 대상 기간 |
| 2 | 요약 | 신규·실패·휴면 건수, 전체 워크플로우 수 |
| 3 | 신규 워크플로우 | 기간 안에 만들어진 워크플로우 |
| 4 | 에러 현황 | 실패한 실행을 원인별로 묶어 원인과 해결책 정리 |
| 5 | 휴면 워크플로우 | 30일 이상 실행되지 않은 활성 워크플로우 |
| 6 | 확인 필요 | 후속 조치가 필요한 항목 |

### 구역별 규칙

**신규 워크플로우**

- 생성 시각이 대상 기간 안인 워크플로우를 생성 순으로 적는다
- 없으면 "이번 주 신규 워크플로우는 없습니다."라고 적는다

**에러 현황**

- 같은 원인의 실패는 한 항목으로 묶는다
- 서브 워크플로우 실패가 메인으로 전파된 경우도 한 항목으로 묶고, 실제 사고 건수를 적는다
- 상태는 `미해결`, `해결됨`, `조치 불필요` 중 하나로 적는다
- 미해결 항목을 가장 위에 둔다
- 없으면 "이번 주 실패한 실행은 없습니다."라고 적는다

**휴면 워크플로우**

- 활성 워크플로우 중 마지막 실행이 30일 이상 지난 것을 적는다
- 해당이 없어도 활성 워크플로우별 마지막 실행 기록은 적는다
- 성공 실행을 저장하지 않는 워크플로우는 기록이 실제보다 오래돼 보이므로 괄호로 표시한다

**확인 필요**

- 리포트 항목에는 들지 않지만 후속 조치가 필요한 것을 적는다 (에러 워크플로우 미지정, 대기 중 실행, 스케줄 지연 등)
- 없으면 구역을 뺀다

### 템플릿

```markdown
# n8n 주간 운영 리포트 ({시작일 MM-DD 요일} ~ {종료일 MM-DD 요일})

**요약**
- 신규 워크플로우 **{N}개**
- 실패 실행 **{N}건**, 원인 {N}가지: 해결 {N}, 조치 불필요 {N}, **미해결 {N}**
- 30일 이상 휴면인 활성 워크플로우 **{N}개**
- 전체 워크플로우 {N}개 (활성 {N}, 비활성 {N})

## 1. 신규 워크플로우
- `{워크플로우 이름}`: {MM-DD HH:mm} 생성, {활성|비활성}, 노드 {N}개

## 2. 에러 현황
**① `{워크플로우 이름}` ({미해결|해결됨|조치 불필요})**: #{실행 ID}, #{실행 ID} · {MM-DD HH:mm} · {실행 방식}
- 원인: {실패한 노드와 에러 내용}
- 해결책: {한 조치 또는 필요한 조치}
- 영향: {운영 영향, 필요할 때만}

## 3. 휴면 워크플로우
{30일 이상 실행되지 않은 활성 워크플로우 목록 또는 "없습니다" 문장}

활성 {N}개의 마지막 실행 기록:
- `{워크플로우 이름}`: {MM-DD HH:mm} {성공|실패} ({비고, 필요할 때만})

## 확인 필요
- {후속 조치가 필요한 항목}
```

### 예시

2026-11-17에 보낸 리포트에서 구역마다 대표 항목만 남긴 것이다.

```markdown
# n8n 주간 운영 리포트 (11-16 월 ~ 11-17 화)

**요약**
- 신규 워크플로우 **3개** (모두 비활성)
- 실패 실행 **5건**, 원인 3가지: 해결 1, 조치 불필요 1, **미해결 1**
- 30일 이상 휴면인 활성 워크플로우 **0개**
- 전체 워크플로우 15개 (활성 8, 비활성 7)

## 1. 신규 워크플로우
- `[메인] 검색: 네이버 통합검색`: 11-16 21:54 생성, 비활성, 노드 16개

## 2. 에러 현황
**① `[메인] 브리핑: 서울 아침 뉴스` (미해결)**: #462, #464 · 11-16 21:00, 21:02 · 수동 실행
- 원인: 네이버 검색 API가 401 인증 실패를 반환했습니다(크리덴셜 「네이버 검색 API」의 Client ID/Secret이 유효하지 않음). 날씨 노드 2개에는 크리덴셜이 없습니다.
- 해결책: 네이버 Client ID/Secret을 다시 넣거나 SerpApi로 바꾸고, 날씨 노드에 OpenWeatherMap 키를 연결합니다.
- 영향: 비활성 워크플로우라 운영 영향은 없습니다.

**② `[메인] 주식: 국내 종목 선별` (해결됨)**: #800, #878 · 11-17 10:36~10:39 · 폼 실행
- 원인: 선정 종목 10개 중 3개의 뉴스 조회가 실패했고, XML 변환이 그 3개를 버려 종목과 뉴스의 짝이 끊겼습니다. 그래서 선정 기록 저장이 실패했습니다. 서브 워크플로우 실패가 메인으로 전파된 것이라 실제 사고는 1건입니다.
- 해결책: 뉴스 요청이 실패하면 빈 RSS로 채우는 `뉴스 응답 확인` 노드를 추가했습니다. 2분 뒤 재실행부터 성공했습니다.

## 3. 휴면 워크플로우
30일 이상 실행되지 않은 활성 워크플로우는 없습니다. 가장 오래된 워크플로우가 11-10 생성이라 아직 30일이 된 것이 없습니다.

활성 8개의 마지막 실행 기록:
- `[메인] 주식: 국내 종목 선별`: 11-17 12:09 성공
- `[서브] 주식: 일별 시세 가져오기`: 11-16 21:20 성공 (성공 실행을 저장하지 않아 이후 호출은 기록에 없음)
- `[에러] 공통: 실패 알림`: 실행 기록 없음

## 확인 필요
- 폼 응답을 기다리는 `waiting` 실행이 11건 남아 있습니다(`[메인] 검색: 네이버 통합검색` 8건, `example-2` 3건).
- 국내 종목 선별의 11-17 정기 실행이 예정 08:10이 아닌 09:50에 시작됐습니다. 원인은 아직 확인하지 않았습니다.
```
